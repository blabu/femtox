Femtox — code review

Critical Bugs & safety issues

1. Race condition: _lastTimerIndex modified in both ISR and task context without full lock
TimerService() (called from TimerISR) decrements _lastTimerIndex and swaps array entries while holding the MainTime lock — but SetTimerTask() can run concurrently on a single-core MCU if an interrupt fires mid-execution after the lock() call but before _lastTimerIndex++. On MSP430 and ARM Cortex-M without PRIMASK, the lock may be a no-op or the critical section may be too narrow, leading to two writers stomping the same slot. Worst case: a timer entry is silently dropped or an expired timer fires with corrupted arguments.
2. validateMemory() always returns TRUE — logic is inverted
In MemoryUnit.c, the function returns TRUE immediately when blocSize is non-zero (line ~310), then tries to accumulate i — but the early return TRUE means the loop body that checks i > HEAP_SIZE is never reached. The function is entirely useless as a validation tool and will hide heap corruption in production.
3. delAllTask() has a broken spin-loop that can hang forever
The implementation is while(countBegin != countEnd) { countBegin = countEnd = 0; }. Setting both to 0 makes the condition false immediately on the first iteration — the loop is harmless but the guard is pointless. More critically, this is called without any lock, so if the scheduler is running, it can race with SetTask from an ISR to produce a half-zeroed queue state. Should simply be an atomic countBegin = countEnd = 0 inside a critical section.
4. ALLOC_MEM heap: freeMem() does not update sizeAllFreeMemmory
When a block is freed, the accounting variable is never incremented. getFreeMemmorySize() therefore always reads stale data and triggers a spurious defragmentation() on every call once any memory has been freed. On constrained MCUs this wastes CPU time proportional to heap size.
5. getTick() spin-read on multi-byte volatile is not atomic on 8/16-bit targets
GlobalTick is a multi-byte type read with while(time_res != GlobalTick) time_res = GlobalTick. On AVR or MSP430 (8/16-bit buses), reading a 32-bit value is not atomic even with this retry loop — the ISR can fire between the high and low byte reads. The result is a silently inconsistent tick value, which can corrupt timer scheduling.

Warning Significant problems

6. Power-save mode: recursive TimerISR() call inside SetTimerTask()
When _PWR_SAVE is active and a new timer is shorter than the current _minTimeOut, SetTimerTask calls TimerISR() directly from task context. This is dangerous: if a real hardware ISR fires at the same time, both contexts run the same timer update code simultaneously, corrupting _lastTimerIndex and timer entries.
7. memSet() custom implementation: incorrect UB on type-punned pointer arithmetic
The 32/64-bit fast path casts a void* to u32*/u64* and dereferences without verifying alignment. On ARM Cortex-M0 and MSP430, unaligned 32-bit writes cause a hardware fault. The byte-level fallback loop also uses (byte_ptr)destination++, which modifies the local copy of the pointer — this is technically fine in C99 but confusing and inconsistent with how memCpy handles it.
8. getFreePositionForTask() — spin-read of countBegin/countEnd is not safe
The function uses separate spin-loops for countBegin and countEnd individually, but there is a window between the two reads where both can change together. The computed free count can be negative (wrapping as u8) or too large. Should read both inside a single critical section.
9. ALLOC_MEM_LARGE: defragmentation() called without result returned to caller
After defragmentation in the large-heap allocMem, _allocMem is retried once. If it fails again, NULL is returned to the caller with no error handler invoked — unlike the timer subsystem which calls MaximizeErrorHandler. Callers rarely check for NULL, making heap exhaustion a silent source of corruption.

Improvement Suggestions for production use

1
Replace all spin-reads with proper critical sections. Every volatile multi-byte variable (GlobalTick, countBegin/countEnd, _lastTimerIndex) should be read and written inside a single lock/unlock pair, not guarded by retry loops. The retry approach gives the illusion of safety but fails on non-atomic bus accesses.
2
Add a watchdog-kick site in Idle(). The current idle hook is user-extensible via SetIdleTask, but there is no guaranteed watchdog refresh. On long-running embedded systems, a runaway task that starves the idle path will silently reset the device without a diagnostic.
3
Make MaximizeErrorHandler configurable and non-silent in release builds. Today it calls into the user's hook or silently does nothing. For safety-critical code, it should at minimum blink an LED, log to a ring buffer in NVRAM, or trigger a watchdog reset with a stored reason code.
4
Add return values to SetTask and SetTimerTask. Both functions currently call the error handler on overflow but return void, so callers cannot react to a failed enqueue. Returning a bool_t or error code lets the application implement retry or drop logic instead of crashing.
5
Separate ISR-safe and task-safe APIs. Functions like SetTask are called from both ISRs (TimerService) and task context. ISR-context calls must disable only the relevant interrupt, not all interrupts via a global lock. Introduce SetTask_fromISR variants (as FreeRTOS does) to make the calling context explicit and avoid over-locking.
6
Add alignment guarantees to the heap allocator. Neither ALLOC_MEM nor ALLOC_MEM_LARGE aligns returned pointers to the target's natural word size. Any struct containing a 32-bit field allocated from this heap will cause unaligned access faults on Cortex-M0 and MSP430. Round allocation sizes up to sizeof(void*) alignment at minimum.
7
Fix or remove validateMemory() and add a real heap integrity check. The function is broken (see bug #2 above). A correct implementation should walk all blocks, verify that getNextBlockSize never produces a size that would walk past HEAP_SIZE, and count free vs allocated bytes to cross-check against sizeAllFreeMemmory.
8
Add CI and a host-side unit test suite. The repo has a CMake x86 target but no tests. Even simple tests — enqueue N tasks, fire timers, verify callback order, alloc/free in various patterns — would have caught bugs #2 and #4 immediately. The x86 platform target makes this entirely feasible without any hardware.
